    CMake¶

    Tài liệu này giới thiệu CMake ở mức đủ để đọc và viết CMakeLists.txt cho một project C/C++ nhỏ, đồng thời biết cách dùng CMake để cross-compile cho embedded Linux. Nên đọc bài Makefile trước.

    Lịch sử và vị trí của CMake¶

    CMake do Kitware phát triển từ khoảng năm 2000, ban đầu phục vụ project ITK (xử lý ảnh y tế), cần build trên nhiều nền tảng khác nhau. Viết Makefile bằng tay cho từng nền tảng (Linux, Windows, macOS) rất tốn công và dễ sai, nên CMake ra đời để mô tả project một lần rồi sinh ra build file phù hợp cho từng môi trường.

    Điểm quan trọng: CMake không phải build tool, mà là một build system generator (meta-build system). Nó không trực tiếp gọi compiler, mà sinh ra Makefile, build.ninja (hoặc project Visual Studio, Xcode...) để make/ninja thực thi.

    CMakeLists.txt --(configure + generate)--> Makefile / build.ninja --(build)--> binary
                      cmake                        make / ninja

    Một số công cụ cùng nhóm để so sánh:

    Công cụ Đặc điểm
    Make Viết tay, đơn giản, phụ thuộc nhiều vào shell/nền tảng
    Autotools ./configure && make, phổ biến ở các project GNU cũ, cú pháp phức tạp
    CMake Phổ biến nhất cho C/C++, có toolchain file cho cross-compile
    Meson Cú pháp gọn, dùng Ninja, ngày càng phổ biến (GNOME, systemd)
    Bazel Dành cho monorepo lớn, build hermetic

    Cài đặt và quy trình cơ bản¶

    sudo apt install cmake ninja-build   # Debian/Ubuntu
cmake --version

    Quy trình chuẩn gồm hai bước: configure/generate rồi build. Nên dùng out-of-source build, tức thư mục build tách khỏi source.

    cmake -S . -B build              # -S: source dir, -B: build dir
cmake --build build              # build (gọi make hoặc ninja bên dưới)
cmake --install build --prefix /usr/local

    Chọn generator bằng -G:

    cmake -S . -B build -G Ninja
cmake -S . -B build -G "Unix Makefiles"   # mặc định trên Linux

    Out-of-source build là gì?

    Toàn bộ file sinh ra (CMakeCache.txt, Makefile, object file, binary) nằm trong thư mục build/, source tree không bị "bẩn". Muốn dọn sạch chỉ cần xoá thư mục build/. Đây là lợi thế lớn so với in-source build kiểu Autotools/Makefile viết tay.

    Ví dụ tối thiểu (Hello World)¶

    hello/
├── CMakeLists.txt
└── main.c

    cmake_minimum_required(VERSION 3.16)
project(hello LANGUAGES C)

add_executable(hello main.c)

    cmake -S . -B build
cmake --build build
./build/hello
    • cmake_minimum_required: yêu cầu phiên bản CMake tối thiểu, đồng thời quyết định các policy (hành vi) mặc định.
    • project: đặt tên project và ngôn ngữ sử dụng.
    • add_executable: tạo một target tên hello từ main.c.

    Khái niệm cốt lõi¶

    Target và Property¶

    Trong CMake hiện đại, mọi thứ xoay quanh target. Một target là một sản phẩm build (executable hoặc library) kèm theo các property của nó (include path, compile flag, thư viện phụ thuộc...).

    add_executable(app main.c)                 # executable
add_library(mylib STATIC mylib.c)          # static library (.a)
add_library(myshared SHARED myshared.c)    # shared library (.so)
add_library(myheader INTERFACE)            # header-only, không có file biên dịch

    Modern CMake: các lệnh target_*¶

    Thay vì đặt biến/flag toàn cục, hãy gắn thuộc tính trực tiếp vào từng target:

    target_include_directories(mylib PUBLIC include)
target_compile_definitions(mylib PRIVATE DEBUG_LOG=1)
target_compile_options(mylib PRIVATE -Wall -Wextra)
target_link_libraries(app PRIVATE mylib)

    PUBLIC / PRIVATE / INTERFACE

    Từ khoá này quyết định thuộc tính có lan truyền sang target phụ thuộc hay không:

    Từ khoá Dùng cho chính target Truyền cho target link tới nó
    PRIVATE Có Không
    PUBLIC Có Có
    INTERFACE Không Có

    Ví dụ: mylib đặt include/ là PUBLIC, thì app link tới mylib sẽ tự động có -Iinclude, không cần khai báo lại. Còn -DDEBUG_LOG=1 là PRIVATE nên chỉ ảnh hưởng nội bộ mylib.

    Cú pháp kiểu cũ

    Khi đọc code cũ sẽ gặp include_directories(), add_definitions(), link_directories() hay gán thẳng CMAKE_C_FLAGS. Chúng áp dụng cho toàn bộ project từ điểm gọi trở xuống, khó kiểm soát. Với code mới nên dùng target_*.

    Biến, Cache và Option¶

    set(SRCS main.c util.c)                      # biến thường
message(STATUS "Sources: ${SRCS}")           # tham chiếu bằng ${VAR}

option(ENABLE_TESTS "Build unit tests" ON)   # biến bool trong cache
if(ENABLE_TESTS)
  add_subdirectory(tests)
endif()

    Giá trị có thể truyền từ command line bằng -D:

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DENABLE_TESTS=OFF

    Các giá trị này được lưu trong cache (build/CMakeCache.txt), nên những lần chạy cmake sau vẫn nhớ. Một số biến chuẩn thường gặp:

    Biến Ý nghĩa
    CMAKE_BUILD_TYPE Debug, Release, RelWithDebInfo, MinSizeRel
    CMAKE_C_COMPILER / CMAKE_CXX_COMPILER Compiler sử dụng
    CMAKE_C_STANDARD / CMAKE_CXX_STANDARD Chuẩn ngôn ngữ (11, 17...)
    CMAKE_INSTALL_PREFIX Thư mục đích khi install
    CMAKE_SOURCE_DIR / CMAKE_BINARY_DIR Thư mục source / build gốc
    CMAKE_CURRENT_SOURCE_DIR Thư mục của CMakeLists.txt đang xử lý

    Điều kiện, vòng lặp, function/macro¶

    if(CMAKE_SYSTEM_NAME STREQUAL "Linux")
  target_sources(app PRIVATE linux_impl.c)
elseif(WIN32)
  target_sources(app PRIVATE win_impl.c)
endif()

foreach(f IN ITEMS a b c)
  message(STATUS "item: ${f}")
endforeach()

function(add_my_tool name)
  add_executable(${name} ${name}.c)
  target_link_libraries(${name} PRIVATE mylib)
endfunction()

    function có scope riêng cho biến, còn macro thì thay thế văn bản trực tiếp vào nơi gọi. Thông thường nên ưu tiên function.

    Quản lý nhiều thư mục¶

    Mỗi thư mục con có CMakeLists.txt riêng, thư mục cha gọi add_subdirectory:

    project/
├── CMakeLists.txt
├── lib/
│   ├── CMakeLists.txt
│   ├── include/mylib.h
│   └── mylib.c
└── app/
    ├── CMakeLists.txt
    └── main.c

    # project/CMakeLists.txt
cmake_minimum_required(VERSION 3.16)
project(demo LANGUAGES C)

add_subdirectory(lib)
add_subdirectory(app)

    Target tạo ở thư mục con có thể được tham chiếu từ thư mục khác (ví dụ app link tới mylib) mà không cần đường dẫn.

    Ví dụ hoàn chỉnh¶

    Project gồm một library, một app, một test, có option và install.

    # CMakeLists.txt (gốc)
cmake_minimum_required(VERSION 3.16)
project(demo VERSION 1.0 LANGUAGES C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

option(BUILD_TESTING "Build tests" ON)

add_subdirectory(lib)
add_subdirectory(app)

if(BUILD_TESTING)
  enable_testing()
  add_subdirectory(tests)
endif()

    # lib/CMakeLists.txt
add_library(mylib STATIC mylib.c)
target_include_directories(mylib PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>)
target_compile_options(mylib PRIVATE -Wall -Wextra)

    # app/CMakeLists.txt
add_executable(app main.c)
target_link_libraries(app PRIVATE mylib)

install(TARGETS app RUNTIME DESTINATION bin)

    # tests/CMakeLists.txt
add_executable(test_mylib test_mylib.c)
target_link_libraries(test_mylib PRIVATE mylib)
add_test(NAME mylib_basic COMMAND test_mylib)

    Trong ví dụ trên:

    • mylib khai báo include/ là PUBLIC, nên app và test_mylib tự có include path, chỉ cần target_link_libraries.
    • $<BUILD_INTERFACE:...> là generator expression, ở đây giới hạn đường dẫn chỉ dùng khi build (không đưa vào bản install).
    • CMAKE_EXPORT_COMPILE_COMMANDS sinh ra build/compile_commands.json để IDE/clangd hiểu project.
    • install(TARGETS ...) cho phép cmake --install đặt app vào <prefix>/bin.
    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
cmake --install build --prefix ./out

    Phụ thuộc bên ngoài¶

    # Thư viện có CMake config hoặc Find module
find_package(Threads REQUIRED)
target_link_libraries(app PRIVATE Threads::Threads)

# Thư viện chỉ có pkg-config (.pc)
find_package(PkgConfig REQUIRED)
pkg_check_modules(LIBUDEV REQUIRED IMPORTED_TARGET libudev)
target_link_libraries(app PRIVATE PkgConfig::LIBUDEV)
    • find_package tìm thư viện đã cài sẵn (trong sysroot nếu cross-compile) và tạo imported target như Threads::Threads, nên link bằng target thay vì đường dẫn thủ công.
    • pkg_check_modules là cầu nối với pkg-config, rất hay gặp khi làm việc với các thư viện hệ thống Linux.
    • FetchContent cho phép tải source của dependency (ví dụ từ Git) ngay lúc configure. Tiện cho project nhỏ, nhưng với embedded thường tránh vì build cần chạy offline và tái lập được.

    Cross-compile cho Embedded Linux¶

    CMake cross-compile thông qua toolchain file, mô tả target system và toolchain. Ví dụ cho ARM 32-bit (toolchain-arm.cmake):

    set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR arm)

set(CMAKE_C_COMPILER   arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER arm-linux-gnueabihf-g++)

# sysroot chứa header và thư viện của target
set(CMAKE_SYSROOT /opt/sysroots/cortexa9hf-neon-poky-linux-gnueabi)

# Chương trình (cmake, python...) tìm ở host; thư viện, header, package chỉ tìm trong sysroot
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

    cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=$PWD/toolchain-arm.cmake
cmake --build build-arm
file build-arm/app    # ELF 32-bit LSB executable, ARM

    Với AArch64, đổi CMAKE_SYSTEM_PROCESSOR thành aarch64 và compiler thành aarch64-linux-gnu-gcc.

    Đổi toolchain thì phải dùng thư mục build mới

    Compiler và các kết quả dò tìm được lưu trong cache. Nếu đã configure bằng gcc host rồi mới thêm CMAKE_TOOLCHAIN_FILE, kết quả sẽ không đúng. Hãy dùng thư mục build riêng cho mỗi target (build-x86, build-arm) hoặc xoá build/ trước khi đổi.

    Trong Yocto và Buildroot¶

    Hai hệ thống build này tự sinh toolchain file nên không cần viết tay:

    • Yocto: recipe chỉ cần inherit cmake; class này gọi cmake với toolchain file trỏ vào sysroot của recipe, các option thêm qua EXTRA_OECMAKE. Xem Yocto.
    • Buildroot: dùng $(eval $(cmake-package)) trong file .mk của package, thêm option qua <PKG>_CONF_OPTS.

    Vì vậy CMakeLists.txt nên viết sạch, không hard-code đường dẫn compiler hay sysroot, để cùng một source build được cả bằng tay lẫn qua Yocto/Buildroot.

    Công cụ đi kèm¶

    • CTest: enable_testing() + add_test(), chạy bằng ctest. Dùng được cả với test chạy trên target qua wrapper (ví dụ qemu) bằng CMAKE_CROSSCOMPILING_EMULATOR.
    • CPack: đóng gói (tar.gz, deb, rpm) từ các rule install().
    • CMakePresets.json: lưu sẵn các cấu hình configure/build để cả team và CI dùng chung.
    {
  "version": 3,
  "configurePresets": [
    {
      "name": "arm-release",
      "binaryDir": "${sourceDir}/build-arm",
      "generator": "Ninja",
      "toolchainFile": "${sourceDir}/toolchain-arm.cmake",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Release" }
    }
  ]
}

    cmake --preset arm-release
cmake --build --preset arm-release   # cần khai báo buildPresets tương ứng
    • compile_commands.json: bật bằng CMAKE_EXPORT_COMPILE_COMMANDS=ON, cho phép clangd, clang-tidy và IDE hiểu đúng flag biên dịch.

    Lỗi thường gặp và cách debug¶

    Tình huống Cách xử lý
    Đổi option/toolchain nhưng không có tác dụng Cache cũ còn giữ giá trị: xoá build/ hoặc CMakeCache.txt
    Muốn xem lệnh compiler thật sự được gọi cmake --build build -v (hoặc make VERBOSE=1)
    Không biết biến có giá trị gì message(STATUS "X = ${X}")
    Không rõ dòng nào trong CMakeLists chạy cmake --trace-expand -S . -B build
    Xem các biến/cache hiện tại cmake -L -S . -B build hoặc ccmake build
    Không tìm thấy package Kiểm tra CMAKE_PREFIX_PATH, CMAKE_FIND_ROOT_PATH, và PKG_CONFIG_PATH (cross: PKG_CONFIG_SYSROOT_DIR, PKG_CONFIG_LIBDIR)

    Tránh file(GLOB ...) để liệt kê source

    file(GLOB SRCS *.c) chỉ chạy lúc configure, nên thêm file .c mới mà không chạy lại cmake thì build sẽ không nhận. Nên liệt kê source tường minh trong add_executable/target_sources, hoặc dùng CONFIGURE_DEPENDS nếu bắt buộc phải glob.

    So sánh nhanh Make và CMake¶

    Make CMake
    Vai trò Build tool, thực thi rule Generator, sinh Makefile/Ninja
    File mô tả Makefile CMakeLists.txt
    Tư duy File và rule (target là file) Target là sản phẩm có property
    Header dependency Phải tự khai báo hoặc dùng -MMD Tự động
    Out-of-source build Phải tự tổ chức Mặc định khuyến khích
    Cross-compile Qua biến CROSS_COMPILE, CC Toolchain file
    Đa nền tảng Kém Tốt (Linux, Windows, macOS)
    Độ dễ gỡ lỗi Dễ đọc, rõ ràng Cú pháp riêng, cần quen

    Hai công cụ không loại trừ nhau: CMake thường sinh ra Makefile rồi make thực thi. Các project như Linux kernel, U-Boot, Buildroot vẫn dùng Kbuild/Makefile, còn CMake phổ biến ở các ứng dụng và thư viện userspace.
