    Git¶

    Ba vùng làm việc của Git¶

    Trước khi đi vào các lệnh, cần nắm một file thay đổi sẽ đi qua những vùng nào:

    flowchart LR
    W["Working directory<br/>(file đang sửa)"] -- "git add" --> I["Staging area<br/>(index)"]
    I -- "git commit" --> L["Local repo<br/>(.git)"]
    L -- "git push" --> R["Remote repo<br/>(GitHub, GitLab...)"]
    R -- "git fetch" --> L
    L -- "git switch / checkout" --> W
    R -. "git pull = fetch + merge" .-> W
    • Working directory: các file trên đĩa mà bạn đang sửa.
    • Staging area: nơi gom các thay đổi sẽ đưa vào commit kế tiếp. Nhờ vùng này có thể chỉ commit một phần thay đổi.
    • Local repo: lịch sử commit nằm trong thư mục .git, chưa ai khác thấy.
    • Remote repo: bản trên server. fetch chỉ tải lịch sử mới về local repo, không đụng vào file đang sửa; pull thì tải về và merge luôn vào nhánh hiện tại.

    Commit¶

    git status                   # Xem file nào đã sửa, file nào đã add
git add main.c util.c        # Đưa từng file vào staging area
git add -p                   # Chọn từng đoạn thay đổi để add
git commit -m "message"      # Tạo commit từ những gì đã add
git log --oneline -n 10      # Xem 10 commit gần nhất

    Muốn huỷ một commit, xem mục Xử lý commit lỗi đã đẩy lên remote bên dưới. Lưu ý git reset --hard <hash> không phải là "revert": lệnh này kéo nhánh lùi về commit <hash> và xoá luôn các commit phía sau cùng thay đổi chưa commit, còn git revert tạo commit mới để đảo ngược thay đổi.

    Kết nối repo local với remote¶

    Thêm một remote tên origin cho repo local:

    git remote add origin <link_to_remote_repo>
# Ví dụ:
git remote add origin git@github.com:vutang/test_git_repo.git

    Liệt kê các remote đang có:

    git remote -v

    Kết quả:

    origin  git@github.com:vutang/test_git_repo.git (fetch)
origin  git@github.com:vutang/test_git_repo.git (push)

    Đổi địa chỉ remote (ví dụ chuyển từ HTTPS sang SSH): git remote set-url origin <link_mới>.

    Nhánh (branch)¶

    Commit đầu tiên tạo ra nhánh mặc định. Git cũ đặt tên là master; từ Git 2.28 có thể đổi bằng git config --global init.defaultBranch main, và GitHub/GitLab hiện tạo repo mới với nhánh main. Đẩy nhánh lên remote lần đầu:

    git push -u origin master    # -u: ghi nhớ origin/master là nhánh upstream, lần sau chỉ cần git push

    Các thao tác cơ bản:

    git branch <tên-nhánh>            # Tạo nhánh mới tại commit hiện tại (chưa chuyển sang)
git switch <tên-nhánh>            # Chuyển sang nhánh (cách cũ: git checkout <tên-nhánh>)
git switch -c <tên-nhánh>         # Tạo và chuyển luôn (cách cũ: git checkout -b <tên-nhánh>)
git push -u origin <tên-nhánh>    # Đẩy nhánh lên remote
git branch -a                     # Liệt kê nhánh local và remote

    Lấy một nhánh từ remote về local¶

    Sau khi git fetch, nhánh branch1 của remote xuất hiện dưới dạng remotes/origin/branch1, nhưng chưa có nhánh local tương ứng. Chạy git switch branch1 (hoặc git checkout branch1): nếu chỉ có một remote có nhánh trùng tên, Git tự tạo nhánh local branch1 theo dõi origin/branch1.

    Trước (git branch -a):

    * master
  remotes/origin/HEAD -> origin/master
  remotes/origin/branch1
  remotes/origin/master

    Sau:

    * branch1
  master
  remotes/origin/HEAD -> origin/master
  remotes/origin/branch1
  remotes/origin/master

    Merge nhánh¶

    git merge luôn gộp nhánh được chỉ định vào nhánh đang đứng. Vì vậy phải chuyển sang nhánh đích trước:

    git switch master        # Nhánh đích
git merge branch1        # Gộp branch1 vào master

    Nếu master không có commit mới nào kể từ khi branch1 rẽ ra, Git chỉ cần đẩy con trỏ master lên đầu branch1 (fast-forward), không tạo merge commit. Muốn luôn có merge commit để lịch sử ghi rõ "nhánh này đã được gộp", dùng git merge --no-ff branch1.

    Gộp hai repo Git thành một¶

    Giả sử muốn đưa toàn bộ lịch sử của repo-b vào repo-a:

    cd repo-a
git remote add repo-b <link_repo_b>
git fetch repo-b
git merge repo-b/master --allow-unrelated-histories   # Hai repo không có commit chung nên cần cờ này
git remote remove repo-b

    Nếu hai repo có file trùng tên, nên chuyển nội dung của repo-b vào một thư mục con (commit trong repo-b trước khi merge) để tránh conflict. Tham khảo thêm: https://stackoverflow.com/questions/1425892/how-do-you-merge-two-git-repositories.

    Quản lý và đồng bộ nhánh (master & dev)¶

    Kéo code mới nhất từ master về dev¶

    Sử dụng khi nhánh master có cập nhật mới và bạn muốn lấy các thay đổi đó về dev để tiếp tục làm việc.

    • Sử dụng Merge (an toàn, khuyên dùng): giữ nguyên lịch sử thực tế, tạo thêm 1 merge commit.
    git checkout dev
git fetch origin
git merge origin/master
git push origin dev
    • Sử dụng Rebase (lịch sử thẳng hàng): bốc các commit riêng của dev đặt lên trên cùng của master.
    git checkout dev
git fetch origin
git rebase origin/master
git push origin dev --force-with-lease

    Hình dưới minh hoạ khác biệt giữa hai cách. Ban đầu dev rẽ ra từ B, sau đó master có thêm E, F:

    Xử lý commit lỗi đã đẩy lên remote¶

    Khi nhánh dev đang chứa một commit bị lỗi và bạn muốn hoàn tác nó.

    • Cách an toàn (dùng Revert): tạo một commit mới mang nội dung đảo ngược, không làm hỏng lịch sử chung của team.
    git log --oneline -n 5       # Lấy mã hash của commit lỗi (VD: a1b2c3d)
git revert <mã_commit>       # Tạo commit đảo ngược
git push origin dev          # Đẩy lên remote bình thường

    ---
config:
  theme: base
  themeVariables:

    git1: "#ef6c00"
  themeCSS: '.branchLabel text { fill: #ffffff !important; } .commit-label { fill: var(--md-mermaid-label-fg-color) !important; } .commit-label-bkg { fill: transparent !important; }'

    Commit X vẫn nằm trong lịch sử, commit Revert X mang thay đổi ngược lại nên code trở về như ở B. Người khác đã pull X chỉ cần pull tiếp, không bị lệch lịch sử.

    • Cách xóa vĩnh viễn (dùng Reset): xóa không để lại dấu vết (cần cẩn thận nếu team dùng chung nhánh).
    git reset --hard HEAD~1      # Quay lùi lại 1 commit để bỏ commit mới nhất
git push origin dev --force-with-lease

    reset chỉ di chuyển con trỏ nhánh dev lùi về B. Commit X không còn thuộc nhánh nào nhưng vẫn nằm trong .git một thời gian, có thể cứu lại bằng reflog. Ai đã pull X về máy sẽ bị lệch lịch sử so với remote.

    Đồng bộ tuyệt đối: ép dev giống hệt master (100%)¶

    Sử dụng khi nhánh dev (cả local lẫn remote) bị rác lịch sử quá nhiều và bạn muốn nó trở thành bản sao hoàn hảo của master.

    Warning

    Thao tác này sẽ xoá vĩnh viễn các commit riêng trên dev.

    • Cách A: ghi đè bằng Reset (nhanh chóng)
    git checkout dev
git fetch origin
git reset --hard origin/master          # Ép nhánh local giống hoàn toàn master
git push origin dev --force-with-lease  # Ghi đè nhánh remote trên server
    • Cách B: xóa hẳn và tạo lại (triệt để nhất)
    git checkout master
git pull origin master
git branch -D dev                 # Xóa nhánh dev ở local
git push origin --delete dev      # Xóa nhánh dev trên server
git checkout -b dev               # Tạo nhánh dev mới cứng từ master
git push -u origin dev            # Đẩy nhánh mới lên server

    --force-with-lease khác gì --force¶

    Các lệnh viết lại lịch sử ở trên (rebase, reset) đều cần đẩy đè lên remote. Nên dùng --force-with-lease thay cho --force:

    • --force ghi đè nhánh trên server bất kể trên đó đang có gì. Nếu đồng nghiệp vừa đẩy commit mới lên dev, commit đó sẽ mất.
    • --force-with-lease chỉ ghi đè khi nhánh trên server vẫn trỏ đúng vào commit mà local đang ghi nhận (origin/dev). Nếu server đã có commit mới mà local chưa thấy, lệnh push bị từ chối.

    Điểm yếu: nếu đã chạy git fetch (hoặc IDE tự fetch ngầm) sau khi đồng nghiệp đẩy code, origin/dev đã được cập nhật nên lease vẫn hợp lệ và commit của họ vẫn bị đè. Từ Git 2.30 có thể thêm --force-if-includes để Git kiểm tra thêm rằng commit trên remote đã thực sự nằm trong lịch sử local:

    git push origin dev --force-with-lease --force-if-includes

    Xử lý xung đột (conflict) khi merge hoặc rebase¶

    Khi cùng một đoạn code bị sửa khác nhau ở hai nhánh, Git dừng lại và đánh dấu xung đột ngay trong file:

    <<<<<<< HEAD
code trên nhánh hiện tại
=======
code từ nhánh đang được merge vào
>>>>>>> origin/master

    Quy trình xử lý:

    git status                     # Liệt kê các file xung đột (trạng thái "both modified")
# Mở từng file, giữ lại phần đúng, xoá các dấu <<<<<<<, ======= và >>>>>>>
git add <file>                 # Đánh dấu file đã xử lý xong
git merge --continue           # Hoặc git rebase --continue nếu đang rebase

    Nếu muốn giữ nguyên phiên bản của một phía cho cả file thay vì sửa tay:

    git checkout --ours <file>     # Giữ phiên bản "ours"
git checkout --theirs <file>   # Giữ phiên bản "theirs"
git add <file>

    Ours và theirs bị đảo khi rebase

    Khi merge trên dev, ours là dev và theirs là origin/master. Khi rebase dev lên origin/master, Git đứng trên origin/master rồi áp lại từng commit của dev, nên ours là origin/master (cộng các commit đã áp xong) còn theirs là commit của dev đang được áp.

    Muốn bỏ cuộc và quay về trạng thái trước khi merge/rebase:

    git merge --abort
git rebase --abort

    Cất tạm thay đổi với stash¶

    Dùng khi đang sửa dở mà phải chuyển nhánh gấp (ví dụ sửa lỗi khẩn trên master), nhưng chưa muốn tạo commit.

    git stash push -m "wip: driver SPI"  # Cất thay đổi, thư mục làm việc trở về sạch
git stash list                       # Xem danh sách: stash@{0}, stash@{1}, ...
git stash pop                        # Lấy stash mới nhất ra và xoá nó khỏi danh sách
git stash apply stash@{1}            # Lấy một stash cụ thể, vẫn giữ lại trong danh sách
git stash drop stash@{1}             # Xoá một stash
git stash show -p stash@{0}          # Xem nội dung chi tiết của stash

    Mặc định stash chỉ cất các file đã được Git theo dõi. Thêm -u (--include-untracked) để cất cả file mới tạo chưa git add.

    Chép commit giữa các nhánh với cherry-pick¶

    Dùng khi chỉ cần một vài commit cụ thể từ nhánh khác, không muốn merge cả nhánh. Ví dụ: một bản vá lỗi đã commit trên dev cần đưa ngay lên master.

    git checkout master
git cherry-pick a1b2c3d               # Áp lại commit a1b2c3d lên master
git cherry-pick a1b2c3d^..f4e5d6c     # Chép cả dải commit, tính luôn a1b2c3d
git push origin master

    cherry-pick tạo ra commit mới với hash khác, chỉ mang cùng nội dung thay đổi. Khi sau này merge dev vào master, Git thường tự nhận ra thay đổi đã có sẵn, nhưng vẫn có thể phát sinh conflict nếu đoạn code đó bị sửa tiếp. Nếu gặp xung đột trong lúc cherry-pick, xử lý như mục trên rồi chạy git cherry-pick --continue (hoặc --abort).

    Sửa lịch sử trước khi đẩy lên remote¶

    Sửa commit cuối cùng (--amend)¶

    git add file_bi_quen.c
git commit --amend --no-edit       # Gộp thêm file vào commit cuối, giữ nguyên message
git commit --amend -m "message mới" # Chỉ sửa lại message

    Gộp và sắp xếp nhiều commit (rebase -i)¶

    git rebase -i HEAD~3               # Mở editor với 3 commit gần nhất

    Editor hiển thị danh sách commit, commit cũ nhất ở trên cùng. Đổi từ khoá đầu dòng để chọn thao tác:

    Từ khoá Ý nghĩa
    pick Giữ nguyên commit
    reword (r) Giữ commit, sửa lại message
    squash (s) Gộp vào commit phía trên, cho sửa message gộp
    fixup (f) Gộp vào commit phía trên, bỏ message của commit này
    drop (d) Xoá commit

    Có thể đổi thứ tự các dòng để sắp xếp lại commit.

    Cách làm gọn khi phát hiện lỗi nhỏ thuộc về một commit cũ:

    git commit --fixup=a1b2c3d             # Tạo commit "fixup! ..." gắn với a1b2c3d
git rebase -i --autosquash a1b2c3d~1   # Git tự xếp và đánh dấu fixup, chỉ cần lưu editor

    Warning

    --amend và rebase -i đều tạo commit mới thay cho commit cũ. Chỉ nên dùng cho commit chưa đẩy lên remote hoặc trên nhánh riêng của mình. Nếu đã đẩy, phải push --force-with-lease và báo cho những người đang dùng chung nhánh.

    Cứu commit bị mất với reflog¶

    Sau khi reset --hard nhầm hoặc rebase hỏng, commit chưa mất ngay. Git ghi lại mọi lần HEAD di chuyển vào reflog, nên vẫn tìm lại được hash của commit cũ:

    git reflog -n 10
# a1b2c3d HEAD@{0}: reset: moving to HEAD~1
# 9f8e7d6 HEAD@{1}: commit: thêm driver SPI

    git branch rescue 9f8e7d6    # Cách an toàn: tạo nhánh mới trỏ vào commit cần cứu
git reset --hard HEAD@{1}    # Hoặc đưa nhánh hiện tại quay về trạng thái trước lệnh reset

    Giới hạn của reflog:

    • Chỉ tồn tại ở local, không được đẩy lên remote; clone mới sẽ không có.
    • Commit không còn nhánh nào trỏ tới sẽ bị dọn sau một thời gian (mặc định 30 ngày, theo gc.reflogExpireUnreachable).
    • Thay đổi chưa từng commit (chưa commit, chưa stash) bị reset --hard xoá thì không cứu được bằng reflog.

    So sánh lịch sử giữa hai nhánh¶

    git log --oneline --graph --all -n 20   # Vẽ đồ thị các nhánh
git log master..dev --oneline           # Commit có trên dev nhưng master chưa có
git log dev..master --oneline           # Commit có trên master mà dev chưa có
git diff master..dev                    # So sánh trực tiếp đầu nhánh master với đầu nhánh dev
git diff master...dev                   # Chỉ các thay đổi của dev kể từ điểm rẽ nhánh khỏi master

    Với git diff, hai chấm (A..B) tương đương git diff A B. Ba chấm (A...B) so sánh B với điểm chung gần nhất (merge base) của A và B, tức là đúng những gì nhánh B đã thay đổi. Đây cũng là cách các trang như GitHub hiển thị diff của một pull request.

    Dọn dẹp nhánh¶

    git branch --merged master          # Liệt kê các nhánh local đã merge hết vào master
git branch -d feature-x             # Xoá nhánh local (Git từ chối nếu nhánh chưa được merge)
git branch -D feature-x             # Ép xoá, kể cả khi chưa merge
git push origin --delete feature-x  # Xoá nhánh trên server
git fetch --prune                   # Xoá các remote-tracking branch mà server đã xoá

    Để fetch luôn tự dọn các nhánh remote đã bị xoá:

    git config --global fetch.prune true

    Bảng tra nhanh¶

    Tình huống Lệnh
    Lấy code mới từ master về dev git merge origin/master hoặc git rebase origin/master
    Hoàn tác commit đã đẩy lên nhánh chung git revert <hash>
    Bỏ commit chưa đẩy git reset --hard HEAD~1
    Đang sửa dở, cần chuyển nhánh git stash push -u rồi git stash pop
    Lấy một commit từ nhánh khác git cherry-pick <hash>
    Thêm file quên vào commit cuối git commit --amend --no-edit
    Gộp nhiều commit thành một git rebase -i HEAD~N
    Lỡ reset --hard mất commit git reflog rồi git branch rescue <hash>
    Xem dev có gì mà master chưa có git log master..dev --oneline
    Đẩy đè sau khi viết lại lịch sử git push --force-with-lease
