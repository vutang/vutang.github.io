    Xilinx Petalinux¶

    Vu Tang - 2/2019

    Phiên bản

    Nội dung trang này ghi chép theo Petalinux 2017.4 và Xilinx SDK 2018.2 (năm 2019). Tên menu, đường dẫn và công cụ có thể đã thay đổi ở các phiên bản Petalinux và Vitis mới hơn.

    Petalinux là bộ công cụ của Xilinx (nay thuộc AMD) dùng để build Linux cho các dòng Zynq-7000, Zynq UltraScale+ và MicroBlaze. Petalinux dựa trên Yocto Project: các lệnh petalinux-* là lớp bọc quanh BitBake và các layer của Xilinx, nên để hiểu cách Petalinux hoạt động cần nắm nguyên lý của Yocto (xem Yocto).

    Các phiên bản¶

    Petalinux 2015.4 & 2014.2¶

    Petalinux 2017.4¶

    Phiên bản 2017.4 thể hiện rõ việc Petalinux dựa trên Yocto: cấu trúc project và cách thêm package đều theo mô hình recipe và layer của Yocto. Các ghi chú dưới đây viết theo phiên bản này.

    Petalinux 2018.2¶

    Khái niệm Yocto trong Petalinux 2017.4¶

    Khái niệm Yocto Trong Petalinux 2017.4
    Build Directory build/
    Layer lõi layers/core/meta/ (chứa classes/image.bbclass, package_rpm.bbclass, staging.bbclass, image_types.bbclass)
    WORKDIR của recipe build/tmp/work/cortexa9hf-neon-xilinx-linux-gnueabi/<recipe>/<version>-r0
    DEPLOY_DIR_RPM build/tmp/deploy/rpm
    Image recipe petalinux-user-image, rootfs tại build/tmp/work/plnx_arm-xilinx-linux-gnueabi/petalinux-user-image/1.0-r0/rootfs
    Sysroot dùng chung build/tmp/sysroots/plnx_arm

    Sysroot dùng chung build/tmp/sysroots/plnx_arm là nơi do_populate_sysroot đặt header và lib để recipe khác dùng khi build (xem bước ④ ở mục Quy trình build của trang Yocto), không phải thành phần của rootfs.

    Metadata của Petalinux 2017.4 dùng override syntax cũ (dấu _). Khi chuyển sang layer Yocto mới hơn cần đổi sang dấu :.

    Mẹo¶

    Tăng tốc bước kiểm tra sstate

    Bước "Checking sstate mirror object availability" có thể kéo dài rất lâu. Có thể tắt kiểm tra sstate mirror trực tuyến trong petalinux-config > Yocto > sstate (xem thảo luận trên Xilinx Forum).

    Ghi chú¶

    • Target mặc định của petalinux-build là image recipe petalinux-user-image.bb, nằm tại <project>/project-spec/meta-plnx-generated/recipes-core/images/petalinux-user-image.bb.
    • Các file BitBake gốc dùng chung cho mọi project nằm tại <thư mục cài đặt>/components/yocto/source/.
    • petalinux-build -x clean và petalinux-build -x distclean không xóa thư mục download.
    • Xóa thư mục build/tmp buộc phải build lại toàn bộ project (trừ bước tải source), quá trình này mất nhiều thời gian.

    • petalinux-build -x clean gọi bitbake -c clean, còn petalinux-build -x distclean gọi bitbake -c cleansstate. Khác biệt giữa hai task của BitBake:

      • do_clean xóa toàn bộ output của recipe, từ bước unpack trở đi. Lần build sau vẫn có thể lấy lại kết quả từ shared state cache (sstate).
      • do_cleansstate xóa output như do_clean và xóa thêm sstate cache của recipe, nên lần build sau phải build lại từ đầu.
      • do_cleanall xóa thêm cả source đã tải về.

      Xem Reference Manual - Tasks. - Ví dụ WORKDIR của một recipe: build/tmp/work/plnx_arm-xilinx-linux-gnueabi/libsample-tar/1.0-r0.

    Kinh nghiệm thực hành¶

    Tạo và khởi tạo project¶

    Quá trình tạo project (1) và import file hdf (2) giống với Petalinux 2015.4 (các lệnh tương ứng xem trong UG1144).

    ├── config.project
└── project-spec
    ├── attributes
    ├── configs
    │   ├── config
    │   └── rootfs_config
    ├── hw-description
    │   └── metadata
    └── meta-user
        ├── conf
        ├── COPYING.MIT
        ├── README
        ├── recipes-apps
        └── recipes-bsp

    Sau bước (1), project có thư mục project-spec, gồm:

    • configs: các cấu hình của project, thay đổi bằng nhóm lệnh petalinux-config.
    • hw-description: chưa có nội dung.
    • meta-user: các recipe cho ứng dụng của người dùng và BSP. Thư mục con conf chứa cấu hình Yocto của layer meta-user.

    Sau bước (2), cấu trúc thư mục của project như sau:

    ├── build
│   ├── cache
│   ├── conf
│   ├── config.log
│   ├── misc
│   └── tmp
├── components
│   └── plnx_workspace
├── config.project
└── project-spec
    ├── attributes
    ├── configs
    ├── hw-description
    ├── meta-plnx-generated
    ├── meta-user
    └── yocto-layer.log

    Các thư mục mới xuất hiện:

    • build: nơi chạy các giai đoạn build. Kết quả trung gian lưu tại build/tmp. Ở các bước sau, build có thêm thư mục downloads chứa source tải về trong task do_fetch.
    • components: ở các phiên bản Petalinux trước, thư mục này chứa source code của các component do người dùng tự thêm.
    • project-spec/meta-plnx-generated: Yocto layer chứa các recipe cho kernel, core và BSP.

    Todo

    Xác định vai trò của components/plnx_workspace trong Petalinux 2017.4.

    Cấu trúc project đầy đủ xem Appendix A trong UG1144.

    Build project khi không có Internet¶

    Lệnh build là petalinux-build. Bản chất của lệnh này là build target petalinux-user-image của Yocto.

    Cấu hình trước khi build

    • Bước "Checking sstate mirror object availability" chạy rất lâu: tắt kiểm tra này trong petalinux-config > Yocto > sstate (xem mục Mẹo).

    • Dừng build đột ngột (ví dụ bằng Ctrl+C) có thể làm BitBake báo lỗi ở lần chạy sau. Cách khắc phục:

      1. Khởi tạo lại môi trường:

        /home/user/Xilinx/Petalinux/settings.sh
/home/user/Xilinx/Petalinux/components/yocto/source/aarch64/environment-setup-aarch64-xilinx-linux

      2. Xóa file ./build/bitbake.lock.

    Cấu hình của project lưu tại project-spec/configs/config.

    Lỗi ở task do_fetch

    Khi build, Petalinux lấy các gói có sẵn trong thư mục cài đặt, tại <thư mục cài đặt>/components/yocto/downloads. Ngoài ra, Petalinux tải thêm từ Internet các gói như:

    • (1) gcc-source-linaro-6.2-linaro-6.2-r2016.11
    • (2) binutils-cross-arm-linaro-2.27-r2016.10
    • (3) u-boot-mkimage-native-v2016.03+gitAUTOINC+df61a74e68-r0
    • (4) binutils-native-linaro-2.27-r2016.10

    Khi không có kết nối Internet, build báo lỗi, ví dụ:

    • u-boot-mkimage-native-v2016.03+gitAUTOINC+df61a74e68-r0 do_fetch: Fetcher failure

    Như vậy, bản cài đặt mặc định của Petalinux không chứa đủ source cho mọi recipe. Để build offline, cần chép thêm các gói sau vào thư mục download:

    • git2_git.linaro.org.toolchain.binutils-gdb.git, tương ứng với (2) và (4)
    • git2_git.linaro.org.toolchain.gcc.git, tương ứng với (1)

    Linaro

    Linaro là tổ chức do ARM cùng một số hãng bán dẫn thành lập năm 2010, phát triển phần mềm mã nguồn mở cho kiến trúc ARM, trong đó có GCC toolchain. Các gói có chữ linaro trong danh sách trên là bản GCC và binutils do Linaro phát hành, Petalinux dùng chúng làm cross toolchain.

    Dùng kernel source bên ngoài

    Petalinux cho phép build kernel từ một cây source có sẵn trên máy thay cho source mặc định: trong petalinux-config, chọn Linux Components Selection > linux-kernel > ext-local-src, rồi khai đường dẫn tới cây source. Chi tiết xem mục "Configuring Out-of-tree Build" trong UG1144.

    Cần kiểm chứng

    Đường dẫn menu ext-local-src được viết theo UG1144, chưa chạy thử trên Petalinux 2017.4.

    Boot từ SD card¶

    Boot từ SD card làm tương tự hướng dẫn ở mục Zedboard. File rootfs.cpio nằm trong thư mục <project>/images/linux/, sẵn sàng để ghi lên thẻ nhớ.

    Mount SD card khi khởi động¶

    Các bước chi tiết xem PetaLinux Yocto Tips (xilinx-wiki.atlassian.net).

    Thêm package của người dùng¶

    Petalinux quản lý gói phần mềm bằng Yocto. Source code của gói có thể tải từ repository trực tuyến hoặc lưu sẵn trên máy. Mục này lấy ví dụ gói iperf, công cụ phổ biến để đo chất lượng mạng.

    Petalinux tải source code của iperf từ GitHub, sau đó cấu hình, build và tích hợp vào hệ thống.

    Khi tạo một ứng dụng mới, Petalinux tạo recipe tại project-spec/meta-user/recipes-apps. Cấu trúc của recipe như sau:

    vux-iperf/
├── files
│   ├── 0002-Remove-pg-from-profile_CFLAGS.patch
│   └── automake-foreign.patch
├── README
└── vux-iperf.bb
    Ví dụ này build iperf3. File BitBake của recipe lấy từ iperf3 3.6 (layers.openembedded.org), nội dung file iperf3_3.6.bb như sau:

    SUMMARY = "Network benchmark tool"
HOMEPAGE = "http://software.es.net/iperf/"
SECTION = "console/network"
BUGTRACKER = "https://github.com/esnet/iperf/issues"
AUTHOR = "ESNET <info@es.net>, Lawrence Berkeley National Laboratory <websupport@lbl.gov>"
LICENSE = "BSD"
LIC_FILES_CHKSUM = "file://LICENSE;md5=a9a036136b748453e839c0eb8906ef2e"

DEPENDS = "openssl"

SRC_URI = "git://github.com/esnet/iperf.git \
           file://automake-foreign.patch \
           file://0002-Remove-pg-from-profile_CFLAGS.patch \
           "
SRCREV = "88f3ad87f38762081a6d7127890ff5c3a052b06a"

S = "${WORKDIR}/git"

inherit autotools

PACKAGECONFIG[lksctp] = "ac_cv_header_netinet_sctp_h=yes,ac_cv_header_netinet_sctp_h=no,lksctp-tools"

CFLAGS += "-D_GNU_SOURCE"
EXTRA_OECONF = "--with-openssl=${RECIPE_SYSROOT}${prefix}"
BBCLASSEXTEND = "native"
    http://cgit.openembedded.org/meta-openembedded/tree/meta-oe/recipes-benchmark/iperf3/iperf3_3.6.bb?h=master

    Các điểm cần lưu ý trong file vux-iperf.bb:

    Đường dẫn đến source code của package

    Biến SRC_URI chứa đường dẫn tới source code của package. BitBake dùng các đường dẫn này trong task do_fetch. 

    SRC_URI = "git://github.com/esnet/iperf.git \
           file://automake-foreign.patch \
    Trong ví dụ này, SRC_URI trỏ tới git repository của ESnet, nơi có thể xem trực tiếp source code. SRC_URI cũng trỏ tới một file patch lưu trên máy; bản patch này có trên openembedded.org.

    Với source lấy từ git, SRC_URI nhận thêm tham số sau dấu ;, ví dụ git://github.com/esnet/iperf.git;protocol=https;branch=master:

    • protocol: giao thức dùng để fetch source code (mặc định là git).
    • branch: branch chứa revision cần fetch.

    Revision của source code

    Biến SRCREV cho BitBake biết revision nào của source code được dùng để build package.

    SRCREV = "88d907f7fb58bfab5d086c5da60c922e1c582c92"

    License của source code

    Biến LIC_FILES_CHKSUM khai file license trong source và checksum MD5 của file đó:

    LIC_FILES_CHKSUM = "file://LICENSE;md5=d098223e44bdd19585315ee75cd9d2d7"

    Khi nội dung file license thay đổi (ví dụ khi đổi sang revision khác), checksum không khớp và build báo lỗi, buộc người viết recipe kiểm tra lại license. File license không nhất thiết tên là LICENSE; có thể là COPYING hoặc một file source chứa đoạn license.

    petalinux-image.bbappend¶

    File project-spec/meta-user/recipes-core/images/petalinux-image.bbappend chứa danh sách package có thể cài vào hệ thống. Xóa package khỏi file này sẽ ảnh hưởng tới danh sách package trong petalinux-config -c rootfs.

    Tự chạy ứng dụng khi khởi động¶

    Thuật ngữ: update-rc.d, System V

    Ứng dụng được cài vào rootfs dưới dạng binary và thường chỉ chạy khi người dùng gọi. Một số ứng dụng cần tự khởi động cùng hệ thống.

    Cách làm là dùng class update-rc.d.bbclass của Yocto để cài init script kiểu System V vào hệ thống. Class này dùng công cụ update-rc.d của Debian để cài init script một cách an toàn.

    Recipe dưới đây cài một init script vào hệ thống:

    SUMMARY = "Simple iiod-init application"
SECTION = "PETALINUX/apps"
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = "file://iiod-init \
    "

S = "${WORKDIR}"

FILESEXTRAPATHS_prepend := "${THISDIR}/files:"

inherit update-rc.d

INITSCRIPT_NAME = "iiod-init"
INITSCRIPT_PARAMS = "start 99 S ."

do_install() {
    install -d ${D}${sysconfdir}/init.d
    install -m 0755 ${S}/iiod-init ${D}${sysconfdir}/init.d/iiod-init
}

FILES_${PN} += "${sysconfdir}/*"
    Các điểm cần lưu ý trong recipe:

    • inherit update-rc.d: kế thừa class update-rc.d.
    • INITSCRIPT_NAME và INITSCRIPT_PARAMS: các biến của class update-rc.d. Tham khảo thêm tại update-rc.d.bbclass của Yocto ref-manual.
    • Init script của recipe này là iiod-init, khai trong biến INITSCRIPT_NAME. Package cần cung cấp chính script iiod-init.

    Init script phải viết theo kiểu System V init, tối thiểu hỗ trợ các lệnh start, stop và restart để điều khiển chương trình.

    Danh sách image¶

    Các loại image¶

    Tên image Mô tả
    Linux Kernel
    image.bin Kernel và root filesystem ở định dạng binary
    image.elf Kernel và root filesystem ở định dạng ELF
    image.srec Kernel và root filesystem ở định dạng SREC
    image.ub Kernel và root filesystem ở định dạng U-Boot (FIT), có thể kèm device tree
    linux.bin Image binary chỉ chứa kernel, không có filesystem
    romfs.img Image ROMFS ở định dạng binary
    U-Boot
    u-boot.bin U-Boot ở định dạng binary
    u-boot.srec U-Boot ở định dạng SREC
    u-boot-s.bin U-Boot relocatable ở định dạng binary
    u-boot-s.elf U-Boot relocatable ở định dạng ELF
    u-boot-s.srec U-Boot relocatable ở định dạng SREC
    ub.config.img Script cấu hình nền tảng cho U-Boot, ở định dạng binary
    Khác
    Image Kernel image không nén, kết quả trực tiếp của bước build kernel (arch/arm/boot/Image hoặc arch/arm64/boot/Image). Trên ARM64, U-Boot boot file này bằng lệnh booti
    uImage Kernel image có header U-Boot (tạo bằng mkimage), chứa loại hệ điều hành và thông tin nạp. Trong Petalinux, file tương ứng là image.ub
    zImage Kernel image nén, tự giải nén khi chạy
    vmlinux Kernel ở dạng ELF chưa nén, còn symbol, dùng để debug

    image.ub và uImage¶

    Petalinux dùng mkimage để tạo uImage từ Image:

    mkimage -A arm64 -O linux -T kernel -C none -a $${kernel_loadaddr} -e $${kernel_loadaddr} -d "$(PROOT)/build/$(LINUX_KERNEL)/boot/Image" $(IMAGEROOT)/uImage

    Theo man page, mkimage tạo image dùng cho bootloader U-Boot.

    Theo Xilinx Wiki, Image là kernel image không nén, còn zImage là kernel image nén, tự giải nén khi khởi động. Nếu môi trường build có mkimage, file linux-xlnx/arch/arm/boot/uImage được tạo bằng cách thêm header U-Boot vào zImage.

    File .bin và file .elf¶

    File .bin là dữ liệu nhị phân thô, được nạp nguyên vào bộ nhớ tại một địa chỉ cố định. File .elf chứa thêm header, bảng section và thông tin nạp (địa chỉ, entry point, symbol), nhờ đó loader và debugger biết đặt từng phần vào vị trí nào.

    Tham khảo: What is the difference between ELF files and bin files? (StackOverflow).
