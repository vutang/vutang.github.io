    Yocto Project – Tổng quan¶

    Yocto Project là gì?¶

    Yocto Project là dự án mã nguồn mở cung cấp template, công cụ và phương pháp để tạo ra bản Linux tùy biến cho thiết bị nhúng và IoT, không phụ thuộc kiến trúc phần cứng (xem website chính thức). Yocto không phải một distro có sẵn: nó là bộ công cụ để tự build ra distro riêng cho sản phẩm từ mã nguồn.

    Bức tranh tổng thể gồm năm thành phần:

    • BitBake: engine đọc metadata, lập lịch và chạy các task.
    • OpenEmbedded-Core (OE-Core): layer metadata lõi (meta/) chứa recipe và class dùng chung.
    • Poky: bản distro tham chiếu, gồm BitBake + OE-Core + meta-poky + meta-yocto-bsp. Đây là điểm xuất phát thường dùng.
    • Layer: thư mục meta-* gom metadata theo chủ đề (BSP phần cứng, distro, ứng dụng). Nhiều layer chồng lên nhau, khai báo trong bblayers.conf.
    • Metadata: recipe (.bb), append (.bbappend), class (.bbclass), include (.inc) và file cấu hình (.conf).

    Đầu vào là mã nguồn và metadata. Đầu ra là package, image (rootfs + kernel + bootloader) và SDK/toolchain.

    Bài giới thiệu tiếng Việt: Yocto Project và ứng dụng trong việc phát triển các hệ thống nhúng (cppdeveloper.com). Ví dụ áp dụng: i.MX6 (DART-MX6).

    Khái niệm nền tảng¶

    Linux Distribution (distro). Hệ điều hành gồm Linux kernel cùng một tập phần mềm và hệ thống quản lý gói. Danh sách distro có trên DistroWatch.

    Embedded System (ES). Hệ thống máy tính thiết kế cho một tác vụ cụ thể, khác với PC hay server chạy nhiều chương trình đa mục đích.

    Package Management System (PMS). Công cụ cài, gỡ, nâng cấp gói và xử lý dependency (rpm/dnf, dpkg/apt, opkg). Yocto có thể tạo gói theo ba định dạng rpm, deb hoặc ipk, chọn bằng biến PACKAGE_CLASSES.

    Compiled vs Interpreted. Ngôn ngữ compiled (C/C++) được dịch ra mã máy của kiến trúc đích, nên build cho board ARM cần cross-compile. Ngôn ngữ interpreted (Python, shell) chạy qua interpreter trên target, nên image phải chứa interpreter đó.

    Toolchain. Tập công cụ lập trình dùng để tạo ra một sản phẩm phần mềm. Toolchain phổ biến là GNU Toolchain:

    • GNU make: tự động hóa compilation và build.
    • GNU Compiler Collection (GCC): tổ hợp compiler cho nhiều ngôn ngữ.
    • GNU C Library (glibc): core C library gồm header, library và dynamic loader.
    • GNU Binutils: linker, assembler, v.v.
    • GNU Bison: parser generator, thường dùng cùng Flex.
    • GNU m4.
    • GNU Debugger (GDB).
    • GNU build system (autotools): Autoconf, Automake, Libtool.

    Software Development Kit (SDK). Toolchain cộng sysroot của target (header, library) và script thiết lập môi trường, dùng để phát triển ứng dụng ngoài cây Yocto. Yocto tạo SDK bằng bitbake -c populate_sdk <image>.

    Thuật ngữ trong Yocto¶

    Các khái niệm dưới đây được mô tả trong Yocto Project Reference Manual.

    Build Directory (TOPDIR). Khu vực Yocto dùng để build. Các thư mục chính:

    Thư mục Nội dung
    conf/local.conf Cấu hình người dùng, ví dụ MACHINE ??= "var-som-mx6" để chọn target machine
    conf/bblayers.conf Danh sách layer tham gia build
    downloads/ Mã nguồn đã tải về
    sstate-cache/ Shared state cache, cho phép tái dùng kết quả task đã build
    tmp/work/ Thư mục làm việc từng recipe
    tmp/deploy/ Kết quả cuối: images/, rpm/ (hoặc deb/, ipk/), sdk/

    Layer. Thư mục meta-* gom metadata theo chủ đề: BSP phần cứng (meta-xilinx, meta-freescale), distro, hoặc ứng dụng. Layer chồng lên nhau và được khai báo trong bblayers.conf. Layer sau có thể sửa recipe của layer trước bằng file .bbappend mà không cần chép lại recipe.

    MACHINE, DISTRO, Image.

    • MACHINE: phần cứng đích, định nghĩa trong conf/machine/<tên>.conf của BSP layer.
    • DISTRO: chính sách của hệ thống (init system, định dạng package, feature), định nghĩa trong conf/distro/.
    • Image recipe: danh sách package đưa vào rootfs, ví dụ core-image-minimal.

    Recipe và Package. Recipe (.bb) là đơn vị build: file chỉ cho BitBake cách lấy nguồn, build và cài một phần mềm. Application, library, bootloader hay kernel đều được mô tả bằng recipe. Một recipe có thể sinh ra một hoặc nhiều package, khai trong biến PACKAGES. Ví dụ recipe libiio sinh ra libiio, libiio-test (chứa iio_info) và libiio-iiod (chứa IIO daemon).

    Các biến thường gặp khi đọc recipe:

    Biến Ý nghĩa
    PN Tên recipe, ví dụ libiio
    PV Version của phần mềm upstream được đóng gói, ví dụ 0.15+gitAUTOINC+6ecff5d46e
    PR Revision của recipe, tăng khi recipe đổi mà PV không đổi; quy ước reset về r0 khi PV tăng
    WORKDIR ${TMPDIR}/work/${MULTIMACH_TARGET_SYS}/${PN}/${EXTENDPE}${PV}-${PR}
    S Thư mục chứa source đã unpack, mặc định ${WORKDIR}/${BPN}-${PV}
    B Thư mục build; thường trùng S, tách riêng khi build out-of-tree (ví dụ CMake)
    D Thư mục đích của do_install, tức ${WORKDIR}/image

    Lưu ý: chuỗi ${PN}-${EXTENDPE}${PV}-${PR} là tên thư mục trong WORKDIR, không phải tên package nhị phân. Ví dụ thực tế: build/tmp/work/cortexa9hf-neon-xilinx-linux-gnueabi/libiio/0.15+gitAUTOINC+6ecff5d46e-r0.

    BitBake¶

    Yocto xem mỗi phần mềm (SDK, Linux kernel, bootloader, ứng dụng, thư viện, ...) như một món ăn, và BitBake là đầu bếp. Đầu bếp nấu theo công thức (recipe, file .bb) do người yêu cầu viết sẵn, và Yocto có một bộ cú pháp riêng để viết công thức này.

    Về kỹ thuật, BitBake là chương trình viết bằng Python, đóng vai trò task executor: đọc metadata, tính dependency giữa các task rồi chạy chúng, song song khi có thể. BitBake là công cụ độc lập; Yocto là BitBake cộng với metadata của OpenEmbedded-Core.

    Cách chạy cơ bản:

    • bitbake <recipe>: chạy mọi task cần thiết của recipe (đến do_build).
    • bitbake -c <task> <recipe>: chạy riêng một task.
    • bitbake <image>: build toàn bộ image.

    Các lệnh chi tiết hơn nằm ở phần Thực hành.

    Quy trình build¶

    Để "nấu ăn" có quy trình, BitBake chia việc build mỗi recipe thành các task nhỏ. Các task mặc định được định nghĩa trong base.bbclass và các class khác (autotools, package, image, ...). Recipe có thể thay đổi bước nào cần thiết bằng cách định nghĩa lại task. Danh sách task đầy đủ có trong Reference Manual - Tasks.

    Sơ đồ cho thấy hai điểm dễ bị hiểu sai: do_populate_sysroot rẽ nhánh song song từ do_install chứ không nằm sau do_package, và image chỉ được tạo từ package đã đóng gói (feed .rpm), không phải từ thư mục build.

    ① Lấy source và vá¶

    do_fetch → do_unpack → do_patch

    Fetcher tải source theo SRC_URI vào ${DL_DIR}, unpack vào ${WORKDIR} rồi áp các patch lên ${S}.

    ② Cấu hình và build¶

    do_configure → do_compile → do_install

    • do_configure: cấu hình trước khi build, giống chạy ./configure trước make.
    • do_compile: thường gọi make vào Makefile của source; kết quả nằm trong ${B}.
    • do_install: chép file thành phẩm từ ${B} vào ${D} (${WORKDIR}/image). Nội dung ${D} là đầu vào của do_package và do_populate_sysroot.

    ③ Đóng gói¶

    do_package → do_packagedata → do_package_write_rpm

    do_package tách nội dung ${D} thành các package theo biến PACKAGES. Ví dụ source libiio sinh ra libiio, libiio-test (chứa iio_info), libiio-iiod (chứa IIO daemon).

    do_package_write_rpm (định nghĩa trong package_rpm.bbclass) tạo các file .rpm và đặt vào ${DEPLOY_DIR_RPM}, tức build/tmp/deploy/rpm trong Petalinux 2017.4. Bên dưới, hàm này gọi công cụ rpmbuild với SPEC file sinh tự động, chạy ngay trong thư mục làm việc của recipe, ví dụ build/tmp/work/cortexa9hf-neon-xilinx-linux-gnueabi/libiio/0.15+gitAUTOINC+6ecff5d46e-r0. Tham khảo thêm RPM Packaging Guide.

    Định dạng gói chọn bằng PACKAGE_CLASSES: package_rpm, package_deb hoặc package_ipk, tương ứng task do_package_write_rpm, do_package_write_deb, do_package_write_ipk.

    Kiểm tra file .rpm chưa cài: rpm -qip <tên>.rpm (ví dụ lệnh rpm).

    ④ Staging: do_populate_sysroot¶

    Task này định nghĩa trong staging.bbclass. Nó chép một tập con file mà do_install đã cài (mặc định là header, library; thư mục không cần khi build như /etc bị bỏ qua, điều chỉnh bằng SYSROOT_DIRS) vào sysroot-destdir của recipe, ví dụ build/tmp/work/cortexa9hf-neon-xilinx-linux-gnueabi/libiio/0.15+gitAUTOINC+6ecff5d46e-r0/sysroot-destdir/. Sau đó hàm sstate_task_postfunc (trong sstate.bbclass) lưu kết quả vào shared state.

    Mục đích: cho các recipe khác dùng file này lúc build. Khi recipe A khai DEPENDS = "libiio", BitBake chạy libiio:do_populate_sysroot trước, rồi A:do_prepare_recipe_sysroot dựng sysroot riêng của A từ các dependency, và do_configure/do_compile của A tìm header, lib trong đó. Task này không ảnh hưởng trực tiếp đến rootfs.

    Vị trí sysroot khác nhau theo phiên bản: bản cũ dùng sysroot chung build/tmp/sysroots/<machine>, bản mới dùng recipe-sysroot trong ${WORKDIR} và kho build/tmp/sysroots-components.

    ⑤ Tạo image¶

    do_rootfs → do_image_<định dạng> → do_image_complete

    do_rootfs (định nghĩa trong image.bbclass) là task của image recipe, ví dụ petalinux-user-image. Danh sách package khai báo bằng IMAGE_INSTALL; từ đó build system gom thành PACKAGE_INSTALL, là danh sách cuối cùng chuyển cho package manager. Package manager (dnf cho rpm, opkg cho ipk, apt cho deb) cài các gói từ package feed vào ${IMAGE_ROOTFS}, thư mục chứa rootfs đang được dựng. Ví dụ thực tế: build/tmp/work/plnx_arm-xilinx-linux-gnueabi/petalinux-user-image/1.0-r0/rootfs.

    Từ ${IMAGE_ROOTFS}, các task do_image_<định dạng> đóng gói rootfs thành ext3/ext4, cpio, jffs2, ... Với ext3/ext4, bản cũ gọi hàm oe_mkext234fs trong image_types.bbclass, hàm này chạy mkfs.ext3/4. Cuối cùng do_image_complete đưa kết quả ra build/tmp/deploy/images/.

    ⑥ Tạo SDK¶

    bitbake -c populate_sdk <image> đóng toolchain cộng sysroot của target thành file cài đặt .sh trong build/tmp/deploy/sdk/. Biến thể populate_sdk_ext tạo extensible SDK.

    Các task khác cần biết¶

    • do_populate_lic: thu thập license của recipe.
    • do_prepare_recipe_sysroot: dựng sysroot riêng của recipe từ các DEPENDS, chạy trước do_configure.
    • do_build: task mặc định, phụ thuộc vào các task chính của recipe.

    Recipe syntax¶

    Recipe là file text gồm biến, hàm shell/Python và directive. Tên file thường có dạng <tên>_<version>.bb, ví dụ libiio_0.15.bb; PN và PV được suy ra từ tên file.

    Chia sẻ metadata¶

    BitBake cho phép dùng chung metadata qua file include (.inc) và class (.bbclass). Xem thêm mục Sharing Functionality trong BitBake manual.

    • include / require <file>.inc: chèn nội dung file vào recipe; require báo lỗi nếu thiếu file.
    • inherit <class>: kế thừa toàn bộ hàm và biến của class. Ví dụ inherit autotools kế thừa các do_configure, do_compile, do_install chuẩn của autotools.bbclass. Người dùng "override" bằng cách định nghĩa lại hàm hoặc biến đó sau dòng inherit.
    • .bbappend: bổ sung hoặc sửa recipe của layer khác mà không chép lại recipe. Tên phải khớp recipe gốc, % thay cho phần version (libiio_%.bbappend).

    Toán tử gán¶

    Toán tử Ý nghĩa
    = Gán; giá trị được expand khi biến được dùng
    ?= Gán nếu biến chưa có giá trị (mặc định yếu)
    ??= Mặc định yếu nhất, bị ?= ghi đè
    := Gán và expand ngay lúc gán
    += , =+ Nối có dấu cách vào cuối, vào đầu
    .= , =. Nối không thêm dấu cách vào cuối, vào đầu
    :append, :prepend, :remove Xử lý cuối quá trình parse, không tự thêm dấu cách

    Override syntax¶

    Từ Yocto 3.4 (honister), dấu : thay cho _ khi viết override (migration guide 3.4):

    Cũ (trước 3.4) Mới (từ 3.4)
    SRC_URI_append_qemux86 SRC_URI:append:qemux86
    FILES_${PN}-ptest FILES:${PN}-ptest
    RDEPENDS_${PN} RDEPENDS:${PN}

    Tài liệu và layer viết theo cú pháp cũ (như Petalinux 2017.4) phải chuyển đổi khi nâng lên bản Yocto mới.

    Ví dụ recipe¶

    Ví dụ minh họa dưới đây chưa được build thử; cú pháp theo các bản kirkstone đến scarthgap. Từ các bản mới hơn, cần kiểm tra thay đổi về S và thư mục unpack.

LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = "file://hello.c \
           file://Makefile"
S = "${WORKDIR}"

do_compile() {
    oe_runmake
}

do_install() {
    install -d ${D}${bindir}
    install -m 0755 hello ${D}${bindir}/hello
}

    Tách package và thêm patch bằng .bbappend ở layer của dự án:

    # libiio_%.bbappend
FILESEXTRAPATHS:prepend := "${THISDIR}/files:"
SRC_URI += "file://0001-fix-build.patch"

PACKAGES =+ "${PN}-test"
FILES:${PN}-test = "${bindir}/iio_info"

    Thuật ngữ trong BitBake¶

    File download support. BitBake cung cấp cơ chế download, unpack và patch source (tài liệu).

    • Fetcher (downloader): tải source từ repository cục bộ hoặc từ xa theo SRC_URI.
    • Unpacker: giải nén ngay sau khi tải. Hỗ trợ các đuôi .Z, .z, .gz, .xz, .zip, .jar, .ipk, .rpm, .srpm, .deb, .bz2.
    • Patching: các file .patch hoặc .diff khai trong SRC_URI được do_patch áp lên source.

    Dependency. DEPENDS là phụ thuộc lúc build (recipe khác phải qua do_populate_sysroot trước). RDEPENDS:${PN} là phụ thuộc lúc chạy, khiến package khác được kéo vào image.

    Shared state (sstate). BitBake tính signature (hash của input) cho từng task. Nếu signature không đổi, kết quả được lấy lại từ sstate-cache/ thay vì chạy lại. Vì vậy build system không dùng số PE, PV, PR để quyết định có build lại hay không; các số này chủ yếu phục vụ việc đánh version cho package nhị phân.

    Biến BitBake quan trọng¶

    Xem danh sách đầy đủ tại Variables Glossary.

    Biến Ý nghĩa
    SRC_URI Danh sách source (cục bộ hoặc từ xa) dùng để build. Fetcher tải về và áp patch trước các bước tiếp theo
    PACKAGES Danh sách package mà recipe tạo ra
    FILES:${PN} Các file thuộc về một package, dùng khi tách package
    DEPENDS Recipe cần có sẵn lúc build (header, lib trong sysroot)
    RDEPENDS:${PN} Package cần có lúc chạy
    IMAGE_INSTALL Package đưa vào image; khai trong image recipe hoặc local.conf (ví dụ IMAGE_INSTALL:append = " libiio", lưu ý dấu cách ở đầu chuỗi)
    PACKAGE_INSTALL Danh sách cuối cùng chuyển cho package manager. Biến nội bộ của phần dựng image, không sửa trực tiếp mà dùng IMAGE_INSTALL
    PACKAGE_CLASSES Định dạng package: package_rpm, package_deb, package_ipk
    IMAGE_ROOTFS Vị trí rootfs trong lúc đang được dựng
    MACHINE, DISTRO Phần cứng đích và chính sách distro
    DL_DIR, SSTATE_DIR, TMPDIR Nơi lưu source tải về, shared state cache và kết quả build
    DEPLOY_DIR_RPM Nơi đặt các file .rpm đã tạo

    Các biến đường dẫn của recipe (WORKDIR, S, B, D) được mô tả ở mục Thuật ngữ trong Yocto.

    Thực hành: lệnh hay dùng¶

    # Build
bitbake <recipe>                    # build một recipe (đến do_build)
bitbake <image>                     # build cả image
bitbake -c <task> <recipe>          # chạy riêng một task, ví dụ -c compile
bitbake -k <image>                  # tiếp tục build khi một recipe lỗi

# Tìm hiểu recipe
bitbake -c listtasks <recipe>       # liệt kê các task của recipe
bitbake -e <recipe> | grep ^WORKDIR=   # xem giá trị biến sau khi parse
bitbake -g <recipe>                 # xuất đồ thị dependency (task-depends.dot)
bitbake-layers show-layers          # các layer đang tham gia build
bitbake-layers show-appends         # các .bbappend đang áp dụng

# Dọn dẹp, build lại sạch
bitbake -c clean <recipe>           # xóa thư mục làm việc của recipe
bitbake -c cleansstate <recipe>     # xóa cả kết quả trong sstate-cache

# Sửa source của một recipe có sẵn
devtool modify <recipe>             # đưa source ra workspace để sửa
devtool build <recipe>
devtool finish <recipe> <layer>     # xuất thay đổi thành patch trong layer

    Khi gặp lỗi, đọc log tại ${WORKDIR}/temp/log.do_<task> của recipe lỗi; bitbake -e giúp kiểm tra biến có đúng giá trị như mong đợi không.

    Phụ lục: Xilinx Petalinux 2017.4¶

    Petalinux 2017.4 là một thực thể ứng dụng Yocto. Phần này gom các chi tiết riêng của Petalinux, tách khỏi nội dung Yocto chung ở trên. Xem thêm: Petalinux Overview, Petalinux 2017, List of Petalinux Images.

    Khái niệm Yocto Trong Petalinux 2017.4
    Build Directory build/
    Layer lõi layers/core/meta/ (chứa classes/image.bbclass, package_rpm.bbclass, staging.bbclass, image_types.bbclass)
    WORKDIR của recipe build/tmp/work/cortexa9hf-neon-xilinx-linux-gnueabi/<recipe>/<version>-r0
    DEPLOY_DIR_RPM build/tmp/deploy/rpm
    Image recipe petalinux-user-image, rootfs tại build/tmp/work/plnx_arm-xilinx-linux-gnueabi/petalinux-user-image/1.0-r0/rootfs
    Sysroot dùng chung build/tmp/sysroots/plnx_arm

    Sysroot dùng chung build/tmp/sysroots/plnx_arm là nơi do_populate_sysroot đặt header và lib để recipe khác dùng khi build (xem bước ④ ở mục Quy trình build), không phải thành phần của rootfs.

    Metadata của Petalinux 2017.4 dùng override syntax cũ (dấu _). Khi chuyển sang layer Yocto mới hơn cần đổi sang dấu :.

    Cần kiểm chứng

    • Ví dụ recipe hello và các lệnh ở mục Thực hành chưa được chạy thực tế, nên thử trên môi trường Yocto đang dùng.
    • Thông tin về sysroot theo phiên bản (sysroot chung ở bản cũ, recipe-sysroot ở bản mới) đúng về nguyên tắc nhưng chưa xác định mốc phiên bản cụ thể.
    • Hai link manual phiên bản cũ (BitBake 1.6, 2.7) được giữ lại ở mục Recipe syntax và Thuật ngữ trong BitBake vì anchor gốc nằm ở đó; nên thay bằng link hiện hành.
