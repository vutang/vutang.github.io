    Buildroot¶

    Trang này trình bày Buildroot ở mức tổng quan, theo thứ tự: Buildroot là gì và chu kỳ release, cấu trúc source tree, quy trình build và thư mục output/, ví dụ build và chạy trên QEMU, toolchain, cấu hình kernel, U-Boot, BusyBox, tùy biến rootfs, các lệnh thường dùng khi phát triển, và cuối cùng là so sánh với Yocto. Cách viết package và tách phần tùy biến của dự án ra ngoài cây Buildroot được trình bày ở trang Buildroot: package và BR2_EXTERNAL.

    Nội dung đối chiếu với Buildroot manual của bản LTS 2026.02 (source tag 2026.02.3).

    Tổng quan Buildroot¶

    Buildroot là bộ Makefile tự động hóa việc build một hệ thống Linux hoàn chỉnh cho thiết bị nhúng bằng cross-compile (biên dịch trên máy build cho kiến trúc khác, xem Cross compile). Từ một file cấu hình duy nhất, Buildroot sinh ra bốn thành phần: cross-compilation toolchain, root filesystem (rootfs), Linux kernel image và bootloader. Có thể dùng từng phần riêng lẻ, ví dụ dùng toolchain có sẵn và chỉ build rootfs.

    Buildroot đặt mục tiêu đơn giản và chỉ tập trung vào việc tạo rootfs, đúng như tên gọi. Theo FAQ của manual, Buildroot không phải là distro hay bộ sinh distro. Hệ quả trực tiếp:

    • Không sinh binary package (.deb, .ipk), không có package manager trên target. Muốn thêm hoặc bớt phần mềm thì build lại image.
    • Không theo dõi package nào cài file nào. Bỏ chọn một package không xóa file của nó khỏi output/target/; cần build sạch.
    • Không tự phát hiện phần nào cần build lại khi cấu hình thay đổi (xem Khi nào cần build sạch).

    Cấu hình dùng Kconfig, cùng ngôn ngữ và giao diện (menuconfig, nconfig, xconfig) với Linux kernel. Kết quả cấu hình nằm trong file .config ở thư mục output.

    Chu kỳ release¶

    Loại Quy ước Thời gian hỗ trợ
    Release theo quý YYYY.02, YYYY.05, YYYY.08, YYYY.11 Tới bản bugfix đầu tiên của release kế tiếp, ví dụ 2026.05.x hết hỗ trợ khi 2026.08.1 ra
    Bugfix YYYY.MM.N, khoảng hàng tháng Theo release gốc
    LTS (long term support) Release đầu năm, YYYY.02 Tới bản bugfix đầu tiên của LTS năm sau, tức khoảng một năm

    Mỗi chu kỳ gồm hai tháng phát triển trên nhánh master và một tháng ổn định, bắt đầu bằng tag -rc1 và mỗi tuần thêm một release candidate. Với sản phẩm, nên chọn bản LTS và theo các bản bugfix của nó.

    Cấu trúc source tree¶

    Thư mục Nội dung
    arch/ Định nghĩa các kiến trúc CPU được hỗ trợ
    board/ File riêng cho từng board: kernel config, patch, script post-build và post-image, readme.txt
    boot/ Package bootloader (U-Boot, Barebox, GRUB, ...)
    configs/ Các file <board>_defconfig dựng sẵn, hơn 300 file trong bản 2026.02
    docs/manual/ Source của manual, build bằng make manual
    fs/ Logic tạo image rootfs (ext2/3/4, squashfs, ubifs, cpio, tar, ...)
    linux/ Package Linux kernel và các kernel extension
    package/ Mỗi package một thư mục con, khoảng 2900 thư mục trong bản 2026.02
    support/ Script và công cụ nội bộ (kconfig, pkg-stats, script kiểm tra)
    system/ Skeleton của rootfs, chọn init system, các cấu hình hệ thống
    toolchain/ Internal toolchain và các external toolchain dựng sẵn
    utils/ Công cụ cho người phát triển Buildroot (check-package, test-pkg, ...)

    Mỗi thành phần (package, bootloader, kernel) có ít nhất hai file: Config.in mô tả option trong menu cấu hình, và <tên>.mk mô tả cách tải, cấu hình, build và cài đặt.

    Quy trình build¶

    Chuẩn bị máy build¶

    Buildroot chạy trên Linux và cần một số công cụ trên máy build: make (từ 3.81), gcc và g++ (từ 4.8), binutils, bash, patch, perl, tar, cpio, unzip, rsync, file, bc, wget, cùng các gói nén thông dụng. Trên Debian/Ubuntu:

    sudo apt install build-essential which sed make binutils diffutils gcc g++ bash \
  patch gzip bzip2 perl tar cpio unzip rsync file bc findutils gawk wget \
  libncurses-dev python3

    libncurses-dev dùng cho menuconfig. Danh sách đầy đủ nằm trong mục System requirements của manual. Có thể build trong container để cố định môi trường, xem Docker cho môi trường build.

    Ba bước cơ bản¶

    make <board>_defconfig   # nạp cấu hình dựng sẵn vào .config
make menuconfig          # chỉnh cấu hình (tùy chọn)
make                     # build toàn bộ

    Không dùng make -jN ở lệnh top-level: Buildroot build từng package tuần tự và tự truyền số job song song vào bên trong mỗi package (option BR2_JLEVEL; giá trị mặc định 0 nghĩa là số CPU của máy build cộng 1). Build song song ở mức top-level (BR2_PER_PACKAGE_DIRECTORIES) là option riêng, đã có nhưng vẫn ghi là thử nghiệm trong menu.

    Có thể đặt thư mục output ngoài cây source bằng O=:

    make O=../build-qemu qemu_aarch64_virt_defconfig
cd ../build-qemu && make

    Cách này cho phép build nhiều cấu hình từ cùng một cây Buildroot. Trong thư mục output, Buildroot tạo sẵn một Makefile nhỏ, nên các lệnh sau đó chạy trực tiếp tại đó.

    Luồng build và thư mục output¶

    Sau khi có .config, Makefile chính tạo các thư mục output, chuẩn bị toolchain, rồi build các thành phần được liệt kê trong biến TARGETS theo thứ tự dependency. Mỗi package đi qua các bước source, extract, patch, configure, build, install. Cuối cùng, Buildroot hoàn thiện rootfs và tạo image.

    Thư mục Nội dung
    output/build/ Source đã giải nén và kết quả build của từng package, mỗi package một thư mục <pkg>-<version>/
    output/host/ Công cụ chạy trên máy build, gồm cả cross compiler. Đây cũng là nội dung của SDK
    output/staging/ Symlink tới sysroot trong host/: header và thư viện của target, dùng để link các package khác
    output/target/ Rootfs chưa đóng gói, binary đã strip. Chưa có quyền file và device node đúng, nên không dùng làm chroot
    output/images/ Kết quả cuối cùng: kernel, DTB, bootloader, image rootfs
    output/graphs/ Đồ thị sinh từ graph-depends, graph-build, graph-size
    output/legal-info/ Kết quả của make legal-info

    Khác biệt giữa staging/ và target/ là điểm cần nắm: thư viện cài vào staging/ kèm header và file .a, .pc để các package khác build được, còn target/ chỉ chứa phần cần chạy trên thiết bị.

    Ví dụ build và chạy trên QEMU¶

    Ví dụ dùng defconfig qemu_aarch64_virt_defconfig: board ảo virt của QEMU với CPU Cortex-A53. Không cần phần cứng nên dùng được để thử mọi thay đổi trên trang này.

    Chưa chạy thử

    Các lệnh trong mục này lấy từ defconfig, board/qemu/aarch64-virt/readme.txt và board/qemu/post-image.sh của bản 2026.02.3, chưa được chạy thử trong môi trường viết trang. Lần build đầu tải và build toàn bộ toolchain nên mất từ vài chục phút tới hơn một giờ tùy máy.

    git clone https://gitlab.com/buildroot.org/buildroot.git
cd buildroot
git checkout 2026.02.3

make qemu_aarch64_virt_defconfig
make

    Defconfig này khá ngắn, chỉ ghi những gì khác với giá trị mặc định:

    BR2_aarch64=y
BR2_PACKAGE_HOST_LINUX_HEADERS_CUSTOM_6_18=y
BR2_GLOBAL_PATCH_DIR="board/qemu/patches"
BR2_DOWNLOAD_FORCE_CHECK_HASHES=y
BR2_SYSTEM_DHCP="eth0"
BR2_ROOTFS_POST_IMAGE_SCRIPT="board/qemu/post-image.sh"
BR2_ROOTFS_POST_SCRIPT_ARGS="$(BR2_DEFCONFIG)"
BR2_LINUX_KERNEL=y
BR2_LINUX_KERNEL_CUSTOM_VERSION=y
BR2_LINUX_KERNEL_CUSTOM_VERSION_VALUE="6.18.7"
BR2_LINUX_KERNEL_USE_CUSTOM_CONFIG=y
BR2_LINUX_KERNEL_CUSTOM_CONFIG_FILE="board/qemu/aarch64-virt/linux.config"
BR2_LINUX_KERNEL_NEEDS_HOST_OPENSSL=y
BR2_TARGET_ROOTFS_EXT2=y
BR2_TARGET_ROOTFS_EXT2_4=y
# BR2_TARGET_ROOTFS_TAR is not set
BR2_PACKAGE_HOST_QEMU=y
BR2_PACKAGE_HOST_QEMU_SYSTEM_MODE=y

    Một số điểm đáng chú ý trong file:

    • Không có option toolchain nào, nên dùng internal toolchain với C library mặc định là glibc. Init system mặc định là BusyBox.
    • Kernel 6.18.7 dùng config riêng của board, header của toolchain khớp với nhánh 6.18.
    • Rootfs là image ext4. Không có bootloader vì QEMU nạp kernel trực tiếp.
    • BR2_PACKAGE_HOST_QEMU=y build luôn QEMU trong output/host/, nên không phụ thuộc phiên bản QEMU của máy build.
    • post-image.sh đọc dòng lệnh QEMU trong readme.txt của board và sinh script output/images/start-qemu.sh.

    Kết quả trong output/images/ gồm Image (kernel), rootfs.ext4 và start-qemu.sh. Chạy:

    output/images/start-qemu.sh --serial-only

    Script đặt output/host/bin lên đầu PATH để dùng QEMU vừa build (thêm --use-system-qemu để dùng QEMU của máy build). Dòng lệnh QEMU tương đương:

    qemu-system-aarch64 -M virt -cpu cortex-a53 -nographic -smp 1 \
  -kernel output/images/Image \
  -append "rootwait root=/dev/vda console=ttyAMA0" \
  -netdev user,id=eth0 -device virtio-net-device,netdev=eth0 \
  -drive file=output/images/rootfs.ext4,if=none,format=raw,id=hd0 \
  -device virtio-blk-device,drive=hd0

    Đăng nhập bằng root, không có mật khẩu (BR2_TARGET_GENERIC_ROOT_PASSWD mặc định rỗng). Thoát QEMU bằng Ctrl-a x.

    Toolchain¶

    Buildroot hỗ trợ hai cách cung cấp toolchain, chọn trong menu Toolchain:

    Internal toolchain External toolchain
    Nguồn Buildroot build gcc, binutils, C library, kernel headers từ source Dùng toolchain có sẵn: toolchain dựng sẵn mà Buildroot biết (Bootlin, Arm, ...) hoặc toolchain tùy ý (custom)
    Thời gian build Build gcc, binutils, C library ở lần build đầu và sau mỗi lần build sạch Chỉ kiểm tra và copy thư viện vào sysroot
    Tùy biến Chọn phiên bản gcc, C library, bật C++, Fortran, ... Phải khai báo đúng đặc tính của toolchain (libc, C++, RPC, ...) để Buildroot kiểm tra
    Phù hợp Cần kiểm soát hoàn toàn toolchain, hoặc dùng musl, uClibc-ng Toolchain do nhà cung cấp SoC đưa, hoặc muốn rút ngắn thời gian build sạch

    C library có ba lựa chọn với internal toolchain: glibc (mặc định), musl và uClibc-ng. musl và uClibc-ng cho rootfs nhỏ hơn nhưng một số phần mềm chỉ build được với glibc.

    Toolchain trong output/host/ dùng được ngoài Buildroot. make sdk đóng gói output/host/ thành <tuple>_sdk-buildroot.tar.gz. Sau khi giải nén ở máy khác, chạy relocate-sdk.sh ở thư mục gốc của SDK rồi source environment-setup để có các biến CC, CFLAGS, ... trỏ vào toolchain và sysroot.

    Cấu hình kernel, U-Boot và BusyBox¶

    Kernel, U-Boot và BusyBox có cấu hình Kconfig riêng, tách khỏi .config của Buildroot. Buildroot cung cấp target để mở menu của chúng và lưu kết quả về đúng file được khai báo trong cấu hình Buildroot.

    Lệnh Tác dụng
    make linux-menuconfig Mở menuconfig của kernel, sửa trên bản trong output/build/linux-*
    make linux-update-defconfig Lưu cấu hình kernel về file BR2_LINUX_KERNEL_CUSTOM_CONFIG_FILE
    make uboot-menuconfig Mở menuconfig của U-Boot (khi U-Boot dùng Kconfig)
    make uboot-update-defconfig Lưu cấu hình U-Boot về file đã khai báo
    make busybox-menuconfig Mở menuconfig của BusyBox
    make busybox-update-config Lưu cấu hình BusyBox về file BR2_PACKAGE_BUSYBOX_CONFIG
    make savedefconfig Lưu cấu hình Buildroot thành defconfig tối giản, về BR2_DEFCONFIG

    Thay đổi qua menuconfig chỉ nằm trong output/build/ và mất khi make clean. Phải chạy lệnh update hoặc savedefconfig tương ứng để lưu lại, rồi commit file đó cùng dự án. Cách viết cấu hình U-Boot cho board xem U-Boot.

    Tùy biến rootfs¶

    Manual khuyến nghị hai cách, dùng cùng lúc được:

    • Rootfs overlay (BR2_ROOTFS_OVERLAY): cây thư mục được copy đè lên output/target/ sau khi build xong các package. Dùng cho file cấu hình, script init, file tĩnh. Có thể khai báo nhiều overlay, cách nhau bằng dấu cách. Các thư mục .git, file .empty và file kết thúc bằng ~ bị bỏ qua.
    • Post-build script (BR2_ROOTFS_POST_BUILD_SCRIPT): chạy sau khi build xong các package, trước khi đóng gói image. Tham số đầu tiên là đường dẫn target/. Dùng để sửa hoặc xóa file. Nếu một package cài file sai, nên sửa package thay vì dọn bằng script.

    Khi bật BR2_ROOTFS_MERGED_USR, overlay không được chứa /bin, /lib, /sbin vì đó là symlink sang /usr.

    Các cơ chế bổ sung:

    Cơ chế Option Dùng khi
    Users table BR2_ROOTFS_USERS_TABLES Tạo user và group cho daemon
    Device/permission table BR2_ROOTFS_DEVICE_TABLE Đặt owner và quyền cho file, tạo device node tĩnh
    Post-fakeroot script BR2_ROOTFS_POST_FAKEROOT_SCRIPT Thao tác cần quyền root (chown, mknod) ngay trước khi tạo image
    Post-image script BR2_ROOTFS_POST_IMAGE_SCRIPT Ghép image cuối: bảng phân vùng, image SD card, firmware update
    Custom skeleton BR2_ROOTFS_SKELETON_CUSTOM Skeleton mặc định khác hoàn toàn nhu cầu. Không khuyến nghị vì mất các bản sửa của skeleton mặc định

    Bước tạo image cần quyền root (tạo device node, đổi owner). Buildroot dùng fakeroot để giả lập, nên cả quá trình build chạy bằng user thường.

    Post-image script của nhiều board gọi genimage, công cụ tạo image có bảng phân vùng từ một file mô tả genimage.cfg. Ví dụ ở board/raspberrypi/genimage-raspberrypi*.cfg và support/scripts/genimage.sh. Phần này liên quan tới cách tổ chức phân vùng khi cập nhật firmware, xem OTA Update.

    Sửa trực tiếp output/target/ rồi chạy make cũng tạo lại được image, nhưng chỉ phù hợp để thử nhanh vì thay đổi mất khi make clean.

    Lệnh thường dùng khi phát triển¶

    Build lại một package¶

    Lệnh Tác dụng
    make <pkg> Build package và các dependency của nó
    make <pkg>-rebuild Chạy lại build và install, không xóa build directory
    make <pkg>-reconfigure Chạy lại từ bước configure
    make <pkg>-dirclean Xóa output/build/<pkg>-<version>/, lần build sau làm lại từ đầu
    make <pkg>-source Chỉ tải source
    make <pkg>-extract, <pkg>-patch Dừng ở bước giải nén hoặc patch, để xem source sau khi áp patch
    make <pkg>-show-depends, <pkg>-show-rdepends Liệt kê dependency và reverse dependency

    Các lệnh trên chỉ tác động lên package, không tạo lại image rootfs. Cần chạy thêm make (hoặc ghép make <pkg>-rebuild all). Buildroot ghi lại các bước đã xong bằng stamp file .stamp_<bước> trong build directory của package; các lệnh rebuild, reconfigure thực chất xóa stamp file tương ứng.

    Dùng source local¶

    Khi đang phát triển một thành phần (kernel, ứng dụng), sửa trong output/build/ không phù hợp vì thư mục này bị xóa khi make clean. Buildroot cho phép trỏ một package tới thư mục source riêng qua file local.mk đặt cạnh .config:

    LINUX_OVERRIDE_SRCDIR = /home/user/src/linux
MYAPP_OVERRIDE_SRCDIR = /home/user/src/myapp

    Khi có <PKG>_OVERRIDE_SRCDIR, Buildroot không tải và không áp patch, mà dùng rsync copy source vào output/build/<pkg>-custom/. Sau mỗi lần sửa, chạy make linux-rebuild all để chỉ copy file thay đổi, build lại kernel và tạo lại image.

    Khi nào cần build sạch¶

    Buildroot không theo dõi ảnh hưởng của một thay đổi cấu hình. Quy tắc rút ra từ manual:

    Thay đổi Cần làm
    Kiến trúc, biến thể CPU, cấu hình toolchain Build sạch: make clean all
    Thêm package mới make là đủ, trừ khi package là thư viện tùy chọn của package đã build: build lại các package đó hoặc build sạch
    Bỏ một package Build sạch, vì file của package vẫn nằm trong target/
    Đổi sub-option của package make <pkg>-rebuild hoặc -reconfigure
    Sửa overlay, post-build, post-image script make là đủ
    Sửa rootfs skeleton Build sạch

    Khi gặp lỗi build mà không chắc nguyên nhân có phải do build dở dang hay không, build sạch để loại trừ. make clean xóa toàn bộ kết quả build, make distclean xóa cả .config. Thư mục dl/ chứa source đã tải không bị xóa; đặt BR2_DL_DIR ra ngoài để dùng chung giữa nhiều cây Buildroot.

    Phân tích và báo cáo¶

    Lệnh Kết quả
    make graph-depends Đồ thị dependency giữa các package, output/graphs/graph-depends.pdf. Đổi định dạng bằng BR2_GRAPH_OUT=svg
    make <pkg>-graph-depends Đồ thị dependency của một package
    make graph-build Thời gian build từng package (cần Python Matplotlib, Numpy)
    make graph-size Dung lượng rootfs theo package và theo file
    make legal-info Thu thập license, source và patch của mọi package vào output/legal-info/
    make show-info Thông tin package (phiên bản, license, CPE, patch) dạng JSON, đầu vào cho quét CVE
    make printvars VARS='...' In giá trị biến make, dùng khi debug file .mk
    make V=1 In đầy đủ lệnh được chạy
    make list-defconfigs Liệt kê defconfig có sẵn

    make show-info kết hợp với support/scripts/pkg-stats để đối chiếu phiên bản package với cơ sở dữ liệu CVE, xem Quản lý lỗ hổng (CVE).

    So sánh Buildroot và Yocto¶

    Tiêu chí Buildroot Yocto
    Ngôn ngữ mô tả Kconfig và GNU Make Recipe của BitBake (.bb, .bbappend, .bbclass)
    Đơn vị cấu hình Một file .config, lưu thành defconfig local.conf, bblayers.conf, distro và machine config trải trên nhiều layer
    Mở rộng BR2_EXTERNAL Layer meta-*
    Kết quả Image rootfs, kernel, bootloader, SDK Image, binary package (rpm, deb, ipk), SDK, có thể dựng package feed
    Package manager trên target Không có Có thể bật
    Build lại tăng dần Hạn chế; đổi cấu hình lớn phải build sạch Shared state cache (sstate), tự phát hiện task cần chạy lại
    Phạm vi Một sản phẩm, một cấu hình Nhiều sản phẩm, nhiều machine dùng chung metadata

    Từ bảng trên, Buildroot phù hợp khi hệ thống có tập phần mềm cố định, cập nhật theo kiểu thay cả image, và đội phát triển muốn công cụ dễ đọc, dễ debug. Yocto phù hợp khi cần quản lý nhiều sản phẩm cùng lúc, cần package feed, hoặc nhà cung cấp SoC chỉ hỗ trợ BSP dạng layer Yocto. Bài so sánh chi tiết hơn: Buildroot vs Yocto: Differences for Your Daily Job (Luca Ceresoli, ELC 2017).
